# Partitions and Capabilities

Status: normative architecture; transport encodings are target-versioned  
Last revised: 2026-08-14

Partitions divide one project into runtime or process domains. Capabilities are
the only authority-bearing interfaces between domains.

## Initial placement model

The first implementation uses explicit entry modules per domain. It does not
automatically move functions based on inferred effects.

Conceptually:

```ts
export default defineApplication({
  domains: {
    app: { entry: "./src/app.ts", trust: "trusted" },
    renderer: { entry: "./src/renderer.tsx", trust: "sandboxed" },
  },
});
```

The exact configuration API will be finalized with the build planner. Its
semantics are:

- every entry creates one partition root;
- ordinary imports must remain within a partition;
- cross-partition access uses a declared capability interface;
- the compiler validates that a module is not accidentally instantiated in two
  domains with shared-state assumptions;
- inferred effects verify placement and explain violations;
- whole-function relocation is deferred until it can preserve observable
  semantics.

Explicit placement is not throwaway behavior. Automatic placement may later
produce the same partition plan as an optimization, while explicit placement
remains the authoritative override and debugging model.

## Domain model

A domain declares:

- stable ID and entry module;
- trust level;
- target/runtime identity;
- process or in-process isolation;
- granted capabilities;
- dynamic realms, if any;
- resource and startup policy;
- lifecycle relationship to other domains.

Trust levels initially include `trusted` and `sandboxed`. A target may define
more restrictive categories, but cannot weaken `sandboxed` validation.

Separate domains normally use separate processes. A trusted development or
embedded configuration may use separate runtime instances in one process while
preserving the same serialized interface. It may not replace the interface with
shared object calls, because that would hide process-only bugs and authority
assumptions.

## Capability definition

A capability is a finite, versioned set of typed operations implemented by one
domain and callable by explicitly named domains.

Conceptually:

```ts
interface CapabilityDefinition {
  readonly id: string;
  readonly version: number;
  readonly callerDomains: readonly string[];
  readonly providerDomain: string;
  readonly operations: readonly CapabilityOperation[];
  readonly policy: CapabilityPolicy;
}
```

Capability operations are asynchronous across a domain boundary. Source APIs
return `Promise<T>`, `AsyncIterable<T>`, or an explicit remote-handle/stream
type. A synchronous Node or platform API cannot silently become a remote
synchronous call.

## Reachability versus authority

Reachability and authorization are separate inputs:

- Reachability determines which declared operations and adapters are needed.
- Policy determines which caller may perform an operation and with what scope.

An operation that is reachable but not granted is a build error. An operation
that is granted but unreachable is removed from the generated interface and
reported as unused authority.

The privileged receiver validates policy at runtime even when the caller was
generated by the same build. A sandboxed process is treated as compromised.

## Policy

Policy is declarative, reviewable build input. It may scope:

- filesystem roots and access modes;
- executable identities and arguments;
- network origins or address ranges;
- database identities;
- device sensors and platform permissions;
- window, document, plugin, or workspace identities;
- resource counts, sizes, rates, and timeouts.

Policy is attached to a caller/domain instance, not only an operation name.
User-selected resources are represented by brokered tokens where possible so a
renderer never supplies an arbitrary privileged path.

There is no generic `invoke(command, data)` privileged interface.

## Transport-safe value algebra

Initial cross-domain values are closed and recursively composed from:

- booleans and exact numeric scalars;
- finite `number` values under the declared encoding;
- UTF-8 strings with explicit length limits;
- immutable byte buffers;
- immutable records with statically known fields;
- immutable arrays with one transport-safe element type;
- tagged unions with a fixed discriminator;
- optional/nullish values;
- serializable error records;
- explicit transferable buffers;
- remote handles;
- stream endpoints.

The following do not cross directly:

- arbitrary class instances;
- closures and callbacks;
- prototypes or property descriptors;
- cyclic object graphs;
- mutable shared records or arrays;
- native pointers;
- DOM/native objects not represented by remote handles;
- runtime-specific error objects.

Serialization is generated from the static type and bounded before allocation.
The receiver validates tags, lengths, numeric ranges, handle ownership, and
policy before dispatch.

## Wire contract

Every generated interface has:

- protocol family and version;
- operation numeric IDs derived deterministically from the frozen schema;
- request and response schemas;
- maximum encoded sizes or explicit streaming requirements;
- cancellation behavior;
- error schema;
- compatibility digest;
- caller/provider identities.

Within the pre-1.0 workspace, both sides are regenerated atomically and only an
exact protocol digest is accepted. No dual protocol readers are retained.

When independently updated components become a product requirement, protocol
compatibility will be specified at that boundary rather than added implicitly.

## Calls

A remote call carries:

- capability and operation ID;
- caller instance identity;
- request ID;
- encoded arguments;
- cancellation token when cancellable;
- trace context;
- optional deadline.

The provider authenticates the channel, validates the message and policy,
executes the operation, then returns a typed result or transport error.

Ordering is guaranteed per channel only where the capability declares it.
Independent calls may execute concurrently. Application code must await when it
requires sequencing.

## Cancellation and deadlines

Cancellation is cooperative and race-safe:

- the caller may request cancellation after dispatch;
- the provider acknowledges whether work was cancelled or had already settled;
- dropping a local promise does not imply remote cancellation;
- an operation declares whether it is cancellable and what cleanup it performs;
- deadlines are explicit inputs, never inferred from transport timeout alone.

Exactly-once side effects are not promised by generic transport. Operations
requiring retries or idempotency declare an application-level key and policy.

## Streams and backpressure

Streams use a transport endpoint with bounded buffering and explicit credit.

- The consumer grants credit measured in bytes or elements.
- The producer may not exceed granted credit.
- Cancellation closes both endpoints and releases associated handles.
- End, error, and cancellation are distinct terminal states.
- Process exit closes all endpoints with a transport error.

Node streams may be adapted to this model only where their observable behavior
is preserved or a documented Native TypeScript-specific API is used. A remote
Node object is not assumed transparent.

## Transferable buffers

A transferable buffer has exclusive logical ownership during transfer. After a
successful send, the sender's handle is detached and rejects access. The
receiver obtains a new local handle to the same transferred storage or a
platform-required copy with equivalent semantics.

Shared read-only mappings may be used internally. Writable shared memory needs
a separate synchronization specification and is not part of the initial
transport algebra.

## Remote handles

A remote handle contains a provider-issued ID, generation, type identity,
capability scope, and lease. The provider owns the real resource.

- Operations validate caller, type, generation, and capability.
- IDs are unguessable or channel-scoped and never interpreted as pointers.
- Local proxy aliases share one lease entry.
- Explicit disposal sends a release.
- Channel/process death releases all leases owned by that peer.
- Provider invalidation makes later operations fail deterministically.
- Handles cannot be forwarded to another domain unless the capability permits a
  brokered transfer.

## Callbacks across domains

General closures do not cross domains. A callback-shaped API is lowered to one
of:

- a one-shot response;
- an explicit subscription remote handle plus event stream;
- a typed reverse capability implemented by the caller.

This keeps lifetime, cancellation, backpressure, and authority visible.

## Errors

Transport errors use a stable record containing:

- category and code;
- safe message;
- operation and trace ID;
- retryability when known;
- structured, policy-approved details;
- optional causal chain.

Native stack memory, privileged paths, arbitrary platform objects, and raw
exception payloads are not sent to sandboxed callers. Development builds may
join privileged and sandboxed traces in a trusted diagnostic sink.

## Node API placement

Canonical `node:*` source APIs may remain available where semantics fit the
target. Across a domain boundary:

- asynchronous APIs map to explicit capabilities;
- synchronous APIs are rejected unless the caller is in the owning trusted
  domain;
- stateful objects use documented proxies, streams, and remote handles;
- source compatibility is claimed only after behavioral conformance testing.

The initial filesystem projection should begin with a narrow asynchronous
`node:fs/promises` surface. Full Node object transparency is not an architectural
assumption.

## Automatic placement

Future whole-function placement may be added only when analysis accounts for:

- module and global state;
- object identity and mutable captures;
- environment, locale, time, and randomness;
- native and domain effects;
- thrown errors and stack behavior;
- input and result transportability;
- cancellation and latency;
- code duplication and initialization.

Until then, the compiler reports inferred placement constraints and suggests
moving code to an explicit domain entry or capability implementation.

## Conformance tests

The partition suite includes:

- exact protocol digest agreement;
- malformed tags, lengths, ranges, and handle IDs;
- reachable-but-ungranted rejection;
- granted-but-unused authority reporting;
- caller authentication and per-instance scopes;
- request/response, cancellation, and race behavior;
- bounded stream backpressure;
- transferable-buffer detachment;
- remote-handle release and peer death;
- renderer compromise fixtures against privileged receivers;
- identical behavior over process and trusted loopback transports where the
  contract promises it.
